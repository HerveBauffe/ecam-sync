## Code layout notes

- `crates/velo-ble` holds byte formats only (FTMS, heart rate, Zwift controllers) and does no I/O. Put protocol changes here, together with their tests.
- `src-tauri/src/devices.rs` handles Bluetooth I/O through `tauri-plugin-blec`, which uses btleplug on desktop and its own Kotlin backend on Android. It sends these events to the UI: `trainer:data`, `controller:button` (once per press), `controller:raw` and `device:status`.
- `src/lib/devices.ts` holds the typed wrappers the frontend uses for those commands and events. Keep it in sync with `devices.rs`.

## Stack (decided)

- A **Tauri 2** native app, targeting **Android** (the tablet, which is the main device) and **desktop**. The frontend is **Svelte 5 + TypeScript + Vite**.
- It is a **Cargo workspace**:
  - `crates/velo-core`: pure domain logic with no I/O (workout model, ZWO and text parsers, metrics, plan engine, wear, FIT, ride state machine).
  - `crates/velo-ble`: FTMS and Zwift Ride drivers, plus a simulator.
  - `crates/velo-sync`: WebDAV, Garmin, intervals.icu.
  - `src-tauri`: Tauri commands and events, SQLite storage, and the ride engine running on a tokio task.
- Business logic lives in Rust, and the Svelte side only displays it. Types are shared with the frontend through generated TypeScript bindings.

## Product summary

**BikeTo** (folder `~/Projets/biketo`; crate names still use `velo-*`) is an **ERG-first app** for indoor cycling training. It combines ideas from suffer.online, PedalCraft, zwoTrainer and ApexVeloLab, and aims to replace intervals.icu, Dreeve and Strava for one user. There is **no virtual ride or 3D world**: the ride screen shows the workout only.

## Architectural constraints (from the brief)

- **No backend server.** All logic runs client-side. Cross-device sync works by pulling and pushing data to a user-provided **WebDAV** store, so the data model must be serializable to files and handle "pull latest" merges.
- **Primary device is an Android tablet** used during rides. A desktop browser is a secondary target for editing workouts and plans and for reviewing data.
- **Zwift Ride V1 controller** support (BLE) is used for three things: virtual shifting in free ride, app navigation, and in-workout controls (play/pause/skip, harder/easier). The whole ride UI must be navigable with **controller buttons only**, not just touch.
- **Garmin Connect sync**: pull health data (weight, non-cycling activities for TSS) and push or sync calendar, workouts and activities. Outdoor rides carry the bike used, which feeds component wear.
- **UI**: soft colors, **dark mode first** with a toggle. The home page lists workouts cleanly, in the style of suffer.online, and the settings page follows the same style. The workout/ride page is modeled on zwoTrainer's.

## Functional domains

- **Workout builder** with three interchangeable editing modes over one workout model: auto-generation (like zwoWorkoutBuilder), drag-and-drop blocks, and text editing (like intervals.icu syntax). The brief says zwoTrainer's builder can be reused as-is for workouts and plans.
- **Adaptive training plans**: the user can move rides within a week to fit their schedule, and the plan then recalculates so it stays optimal.
- **Fitness analytics**: CTL, ATL, TSB, TSS, readiness, rest days, monotony, polarization, and rolling 7-day distance/time objectives. Use the Dreeve and ApexVeloLab implementations as references.
- **Bike and component wear** (like Dreeve): track mileage per bike and per component by km, time, and so on.
